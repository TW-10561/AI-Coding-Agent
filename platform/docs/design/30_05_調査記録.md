## 1. アーキテクチャ調査（Architecture Investigation）

### 1.1 Investigation: Platform Backend Framework Selection

**Date:** Design Phase  
**Investigator:** Platform Team  
**Question:** Which HTTP framework for the Bun-based backend?

| Candidate | Pros | Cons | Decision |
|-----------|------|------|----------|
| **Hono** | First-class Bun support, 3x faster than Express, EdgeFirst design, built-in middleware | Less mature ecosystem | ✅ SELECTED |
| Express | Most popular, large ecosystem | Not optimized for Bun, adds overhead | ✗ |
| Fastify | High performance | Complex types, no Bun-first support | ✗ |
| Elysia | Bun-first | Less stable, breaking changes | ✗ |

**Rationale:** Hono's native Bun compatibility, ultra-low overhead, and built-in middleware (CORS, rate limiting) made it the clear choice for a production AI platform API.

---

### 1.2 Investigation: Tool Calling Strategy

**Date:** Design Phase  
**Question:** How should the platform communicate tool calls to LLMs?

**Finding:** The AI Gateway (172.30.140.63:9080) routes to multiple cloud providers. Some providers (MiniMax, etc.) do NOT support the native OpenAI `tools[]` JSON parameter format. Sending `tools[]` breaks the API for these models.

**Decision: Text-based XML tool calling**

```
REJECTED: Native JSON function_call
  → Breaks gateway models (MiniMax, etc.)

SELECTED: XML text-based tool instructions
  → TOOL_USE_INSTRUCTIONS added to system prompt
  → Model outputs: <tool_use><name>bash</name>...</tool_use>
  → Platform parses 4 XML/JSON formats for compatibility
  → Works with ANY OpenAI-compatible endpoint
```

**Trade-off accepted:** Slightly more parsing complexity in exchange for universal provider compatibility.

---

### 1.3 Investigation: Database Technology Selection

**Date:** Design Phase  
**Question:** What persistence layer for audit, budget, workspaces, and task state?

| Candidate | Pros | Cons | Decision |
|-----------|------|------|----------|
| **SQLite (bun:sqlite)** | Zero dependencies, embedded, WAL mode, crash-safe, perfect for single-node | Not horizontally scalable | ✅ SELECTED |
| PostgreSQL | Full SQL, scalable | Requires separate server, over-engineering for local AI tool | ✗ |
| Redis | Fast in-memory | Persistence complexity, extra process | ✗ |
| In-memory only | Fastest | Lost on restart — unacceptable for audit/budget | ✗ |

**Rationale:** The platform is a self-hosted single-node tool. SQLite with WAL mode provides crash recovery, ACID transactions, and zero operational overhead — ideal for this use case.

---

### 1.4 Investigation: OpenCode Integration

**Date:** Design Phase  
**Question:** Build AI chat from scratch or wrap an existing engine?

**Finding:** OpenCode (sst/opencode) is a mature, production-ready AI coding engine with:
- Multi-provider session management
- Native tool calling loop
- File operation tools
- Context management

**Decision:** Wrap OpenCode as an internal service rather than rebuild.

```
Platform (:3100) ──wraps──▶ OpenCode (:4096) ──calls──▶ LLM
```

**Rationale:** Saved ~6 months of development time. Platform adds the production wrapper (auth, rate limiting, audit, budget, HITL, skills, orchestration) on top of OpenCode's AI capabilities.

## 2. セキュリティ調査（Security Investigation）

### 2.1 Investigation: HITL Risk Thresholds

**Date:** Design Phase  
**Question:** What risk thresholds should the HITL system use?

**Analysis:**

| Action Class | Risk Score | Justification |
|----------|------------|---------------|
| Read operations (read_file, list_dir, git_status) | 0.0 – 0.1 | Read-only, no destructive potential |
| Write to existing file | 0.20 – 0.35 | Low risk, reversible |
| Write to new file | 0.30 – 0.45 | May create unexpected artifacts |
| Bash command (benign: grep, cat) | 0.20 – 0.35 | Shell but read-only pattern |
| Bash command (write: echo, mkdir) | 0.45 – 0.65 | Creates state change |
| Bash with sudo or privilege escalation | 0.90+ | DENY always |
| rm -rf, DROP TABLE, git push --force | 0.85 – 1.0 | Irreversible, DENY |
| .env access, SSH key read | 1.0 | Always DENY |
| curl to external domains | 0.60 – 0.75 | Data exfiltration risk |

**Thresholds set:**
- `< 0.30` → Auto ALLOW (safe operations)
- `0.30 – 0.69` → Human GATE (ask user)
- `≥ 0.70` → DENY by default (configurable)

---

### 2.2 Investigation: API Authentication Design

**Date:** Design Phase  
**Question:** What authentication model for the platform API?

**Options analyzed:**

| Option | Security | Complexity | Fit |
|--------|----------|------------|-----|
| No auth (open) | Low | None | Default for local dev |
| Static API key | Medium | Very low | ✅ Production default |
| JWT | High | Medium | Future option |
| OAuth 2.0 | Very High | High | Over-engineering |

**Decision:** Optional static API key (`THIRDWAVE_API_KEY` env var).
- If not set → open mode (localhost only)
- If set → enforce `Bearer` or `x-api-key` header

**Rationale:** Keeps local dev friction-free while enabling production security with one env var.

---

### 2.3 Investigation: Rate Limiting Strategy

**Date:** Design Phase  
**Question:** What rate limiting approach for the API?

**Analysis of LLM platform usage patterns:**
- Normal interactive use: 1-5 requests/minute
- Parallel orchestration: burst of 10-20 simultaneous requests
- Agentic loop: 5-15 internal tool calls per user prompt

**Decision:** Sliding window, 120 req/min per IP
- Allows orchestration bursts
- Prevents abuse
- nginx (upstream): 20 req/s burst 50 for public exposure

## 3. UI/UX調査（UI/UX Investigation）

### 3.1 Investigation: TUI vs Web UI

**Date:** Design Phase  
**Question:** Should the primary client be a TUI (terminal) or web UI?

| Factor | TUI | Web UI |
|--------|-----|--------|
| Developer workflow | Native, no context switch | Separate browser |
| Remote SSH development | ✅ Works over SSH | ✗ Requires tunnel or VPN |
| Response speed | Near-instant | Round-trip load |
| Markdown rendering | Good (marked-terminal) | Excellent |
| Code integration | Copy-paste, direct | Button/clipboard |
| GPU server access | ✅ SSH + TUI = perfect | Requires open port |

**Decision:** TUI-first, VS Code Extension as secondary client.

**Rationale:** The primary use case is developers on GPU servers via SSH. TUI works perfectly in this environment where a browser is unavailable or impractical.

---

### 3.2 Investigation: TUI Input Handling Edge Cases

**Date:** Development Phase  
**Question:** How to handle complex input scenarios in the terminal?

**Cases investigated and solved:**

| Case | Problem | Solution |
|------|---------|---------|
| Paste detection | Rapid lines look like commands | 80ms debounce + 3+ line detection |
| Multi-line prompts | `\n` in prompts mis-triggers Enter | Block mode with `"""` delimiter |
| Line continuation | Long prompts split awkwardly | `\` at end of line → continuation |
| Command echo | Input showed twice (readline quirk) | Custom prompt + clearLine sequence |
| Non-blocking status | Background poll interrupted prompts | `processing` flag guards poll output |

---

### 3.3 Investigation: VS Code Extension Architecture

**Date:** Design Phase  
**Question:** Webview vs Tree View vs Language Client?

**Analysis:**

| Approach | Rich UI | Performance | Complexity |
|----------|---------|-------------|------------|
| **Webview + HTML** | ✅ Full HTML/CSS | Medium | Medium |
| Tree View only | Static list | Fast | Low |
| Language Client | Code intelligence | Low for chat | High |

**Decision:** Webview for chat + Tree View for navigation panels.
- Chat uses Webview for markdown, code blocks, tool cards
- Sidebar navigation (sessions, models, skills) uses Tree View for native VS Code look

## 4. パフォーマンス調査（Performance Investigation）

### 4.1 Investigation: Context Window Management

**Date:** Development Phase  
**Question:** How to maximize effective context without exceeding LLM limits?

**Findings:**
- Qwen3-Coder-30B: 32768 token context window
- Each tool call adds ~200-500 tokens to history
- 15 agentic rounds × 500 tokens = 7,500 tokens for tool history alone
- Skill injection adds ~2,000-5,000 tokens

**Decision:** History buffer: last 10 turns (20 messages), ~80-90 char summary per message

```
Budget allocation:
  System prompt:        ~1,000 tokens
  Skill context:        ~3,000 tokens (if injected)
  Conversation history: ~5,000 tokens (10 turns)
  Current prompt:       ~2,000 tokens
  Tool results:         ~5,000 tokens
  Model output:         8,192 tokens (max)
  ────────────────────────────────────
  Total: ~24,192 tokens (within 32768 limit)
```

---

### 4.2 Investigation: Audit Log Performance

**Date:** Development Phase  
**Question:** Synchronous writes to SQLite will block the event loop?

**Finding:** SQLite writes during request handling added 2-8ms latency per API call.

**Solution:** Buffered writes with 5-second flush interval.
```
Request → append to in-memory buffer
                        ↓ (every 5 seconds)
              batch INSERT into audit_events
```

**Result:** Audit overhead reduced to <0.1ms per request.

---

### 4.3 Investigation: Skill RAG Performance

**Date:** Development Phase  
**Question:** Computing relevance for 31 skills for every message — is this fast enough?

**Measurement:**
- 31 skills × keyword similarity scoring = ~5-12ms per message
- Acceptable (adds < 1% to typical 1-3s LLM round-trip)

**Optimization applied:** Skills are preloaded into memory on startup. No disk I/O during search.

## 5. 統合調査（Integration Investigation）

### 5.1 Investigation: Skill System RAG Threshold

**Date:** Development Phase  
**Question:** What relevance threshold triggers skill injection?

**Experiments:**
| Threshold | Precision | Recall | False-inject rate |
|-----------|-----------|--------|------------------|
| 0.50 | 72% | 91% | 28% (too many irrelevant) |
| 0.65 | 84% | 79% | 16% |
| **0.75** | **91%** | **73%** | **9%** ← selected |
| 0.85 | 96% | 52% | 4% (misses relevant skills) |

**Decision:** Threshold = 0.75 (75%) — best balance of precision and recall.

---

### 5.2 Investigation: SSE vs WebSocket for Streaming

**Date:** Design Phase  
**Question:** Server-Sent Events vs WebSocket for streaming LLM output?

| Factor | SSE | WebSocket |
|--------|-----|-----------|
| Server implementation | Simple (Hono built-in) | Requires ws library |
| Client implementation | Simple (EventSource) | More complex |
| Proxy compatibility | ✅ Works through nginx/CDN | Requires upgrade headers |
| Reconnection | ✅ Automatic | Manual |
| Bidirectional | No (server→client only) | Yes (both ways) |
| Our use case fit | ✅ LLM output is server→client | Overkill |

**Decision:** SSE for streaming LLM output. The one-way streaming nature of LLM output maps perfectly to SSE semantics.
