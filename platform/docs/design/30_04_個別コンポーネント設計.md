## 1. RAG / Skill System Design

### 1.1 概要（Overview）

The Skill System provides **RAG (Retrieval-Augmented Generation)** context injection. When a user sends a message, the platform searches installed skills for relevant domain knowledge and injects the top-matching skill into the system prompt.

### 1.2 Skill System Architecture

```
┌──────────────────────────────────────────────────────────────────────┐
│                        SKILL / RAG SYSTEM                             │
└──────────────────────────────────────────────────────────────────────┘

  Installation Phase:
  ┌────────────────────────────────────────────────────────────────┐
  │  platform/skills/                                              │
  │  ├── registry.json          ← master skill index               │
  │  ├── manifests/             ← metadata per skill               │
  │  │    ├── api-design.json   (name, category, description, tags)│
  │  │    └── ...                                                   │
  │  └── installed/             ← full skill content               │
  │       ├── api-design-principles/SKILL.md                       │
  │       ├── architecture-patterns/SKILL.md                       │
  │       └── ... (31 skills total)                                │
  └────────────────────────────────────────────────────────────────┘

  Query Phase (per chat message):
  ┌───────────────────────────────────────────────────────────────────┐
  │                                                                   │
  │  User Message ("optimize the query performance")                  │
  │         │                                                         │
  │         ▼                                                         │
  │  SkillManager.searchSkills(query, topK=1)                        │
  │         │                                                         │
  │  ┌──────┴──────────────────────────────────────────────────────┐ │
  │  │  RELEVANCE SCORING                                           │ │
  │  │                                                              │ │
  │  │  For each skill manifest:                                    │ │
  │  │  1. Tokenize query + skill description + tags                │ │
  │  │  2. Compute cosine similarity (TF-IDF / keyword overlap)     │ │
  │  │  3. Score: 0.0 → 1.0                                        │ │
  │  │  4. Sort descending by score                                 │ │
  │  └──────────────────────────────────────────────────────────────┘ │
  │         │                                                         │
  │   score ≥ 0.75?                                                  │
  │         │                                                         │
  │    ┌────┴────┐                                                    │
  │   YES       NO                                                    │
  │    │         │                                                    │
  │    ▼         ▼                                                    │
```

## 2. Database Schema Design

### 2.1 Overview

All persistence uses **SQLite with WAL mode** via `bun:sqlite`. Tables are created on startup.

### 2.2 Audit Database Schema

```sql
-- Table: audit_events
CREATE TABLE audit_events (
    id          TEXT PRIMARY KEY,    -- ULID (sortable)
    timestamp   INTEGER NOT NULL,    -- Unix ms
    action      TEXT NOT NULL,       -- 'api_request' | 'chat_prompt' | 'tool_exec' | 'policy_decision'
    user_id     TEXT,                -- Optional user identifier
    session_id  TEXT,                -- Associated session
    success     INTEGER NOT NULL,    -- 0 | 1
    duration_ms INTEGER,             -- Response time
    metadata    TEXT                 -- JSON: { method, path, status, model, tokens }
);

-- Index for time-range queries
CREATE INDEX idx_audit_timestamp ON audit_events(timestamp DESC);
CREATE INDEX idx_audit_action    ON audit_events(action);
CREATE INDEX idx_audit_user      ON audit_events(user_id);
```

### 2.3 Budget Database Schema

```sql
-- Table: budget_usage
CREATE TABLE budget_usage (
    id              TEXT PRIMARY KEY,   -- ULID
    timestamp       INTEGER NOT NULL,   -- Unix ms
    user_id         TEXT NOT NULL,
    session_id      TEXT,
    input_tokens    INTEGER DEFAULT 0,
    output_tokens   INTEGER DEFAULT 0,
    total_tokens    INTEGER DEFAULT 0,
    model           TEXT,
    cost_estimate   REAL DEFAULT 0.0    -- USD estimate
);

-- Table: budget_limits
CREATE TABLE budget_limits (
    user_id         TEXT PRIMARY KEY,
    daily_tokens    INTEGER DEFAULT 100000,
    monthly_tokens  INTEGER DEFAULT 2000000,
    updated_at      INTEGER NOT NULL
);

CREATE INDEX idx_budget_usage_user_ts ON budget_usage(user_id, timestamp DESC);
```

### 2.4 Task State Database Schema

```sql
-- Table: tasks
CREATE TABLE tasks (
    id              TEXT PRIMARY KEY,   -- ULID
    type            TEXT NOT NULL,      -- 'simple' | 'orchestration' | 'parallel'
    status          TEXT NOT NULL,      -- 'pending' | 'running' | 'completed' | 'failed' | 'cancelled'
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL,
    started_at      INTEGER,
    completed_at    INTEGER,
    agent_id        TEXT,
    prompt          TEXT,
    result          TEXT,               -- JSON result
    error           TEXT,               -- Error message if failed
    retry_count     INTEGER DEFAULT 0,
    parent_id       TEXT,               -- For subtasks
    metadata        TEXT                -- JSON extra data
);

-- State transition validation (done in application layer)
-- Valid transitions:
--   pending   → running
--   running   → completed | failed | cancelled
--   failed    → pending   (retry)

CREATE INDEX idx_tasks_status    ON tasks(status);
CREATE INDEX idx_tasks_parent    ON tasks(parent_id);
CREATE INDEX idx_tasks_created   ON tasks(created_at DESC);
```

### 2.5 Workspace Database Schema

```sql
-- Table: workspaces
CREATE TABLE workspaces (
    id          TEXT PRIMARY KEY,   -- ULID
    name        TEXT NOT NULL UNIQUE,
    directory   TEXT NOT NULL,
    tags        TEXT,               -- JSON array ["python", "backend"]
    is_active   INTEGER DEFAULT 0,  -- 0 | 1 (only one active at a time)
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL
);

-- Table: workspace_metadata
CREATE TABLE workspace_metadata (
    workspace_id    TEXT NOT NULL,
    key             TEXT NOT NULL,
    value           TEXT,
    PRIMARY KEY (workspace_id, key),
    FOREIGN KEY (workspace_id) REFERENCES workspaces(id)
);
```

## 3. HITL (Human-in-the-Loop) Component Design

### 3.1 Overview

HITL is a safety layer that intercepts agent actions, scores risk, and gates dangerous operations through human approval.

### 3.2 HITL Architecture

```
┌───────────────────────────────────────────────────────────────────────┐
│                    HITL GUARD SYSTEM                                   │
└───────────────────────────────────────────────────────────────────────┘

  Agent wants to execute action
          │
          ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │                    GUARD CHAIN                                    │
  │                                                                   │
  │  Input Action (type + params)                                     │
  │         │                                                         │
  │         ▼                                                         │
  │  ┌────────────────┐    ┌────────────────┐    ┌─────────────────┐ │
  │  │ SensitiveFiles │    │ DestructiveGuard│    │  NetworkGuard   │ │
  │  │ Guard          │    │                │    │                 │ │
  │  │ .env, certs,   │    │ rm -rf, DROP,  │    │ curl to extern, │ │
  │  │ ssh keys, etc  │    │ git push -force│    │ wget, etc       │ │
  │  └───────┬────────┘    └───────┬────────┘    └────────┬────────┘ │
  │          │                     │                       │          │
  │          └──────────┬──────────┘                       │          │
  │                     └────────────────────┬─────────────┘          │
  │                                          ▼                         │
  │                              ┌──────────────────────┐             │
  │                              │    RiskEngine         │             │
  │                              │   .score(action)      │             │
  │                              │                       │             │
  │                              │  Factors:             │             │
  │                              │  - action type        │             │
  │                              │  - file path class    │             │
  │                              │  - network target     │             │
  │                              │  - command pattern    │             │
  │                              │  - skill trust level  │             │
  │                              │  - RBAC role          │             │
  │                              │                       │             │
  │                              │  Output: 0.0 → 1.0    │             │
  │                              └──────────┬────────────┘             │
  │                                         │                          │
  │                              ┌──────────┴────────────┐            │
  │                              │   AUTONOMY CONTROLLER  │            │
  │                              │   Per-agent mode:      │            │
  │                              │   FULL | SEMI | MANUAL │            │
  │                              └──────────┬────────────┘             │
  │                                         │                          │
  │                    ┌────────────────────┼────────────────────────┐ │
  │                    │                    │                        │ │
  │                risk<deny_thresh    deny_thresh≤risk          risk≥1│ │
  │                (auto allow)        <ask_thresh               (deny)│ │
  │                    │               (human gate)                  │ │
  │                    ▼                    │                        ▼ │
  │             ┌────────────┐      ┌───────┴──────────┐    ┌──────────┐│
  │             │  ALLOW     │      │  PAUSE + NOTIFY  │    │  DENY    ││
  │             │  Execute   │      │  Wait for human  │    │  Blocked ││
  │             │  in sandbox│      │  approval        │    │  Log it  ││
  │             └────────────┘      └──────────────────┘    └──────────┘│
  └──────────────────────────────────────────────────────────────────────┘
          │
          ▼
  ┌────────────────────┐
  │   SandboxRunner    │
  │   Execute with     │
  │   restrictions:    │
  │   - no sudo        │
  │   - path limits    │
  │   - timeout        │
  └────────────────────┘
          │
          ▼
  AuditLogger.log(action, decision, outcome)
```

### 3.3 Risk Score Thresholds

| Risk Range | Decision | Example Actions |
|------------|----------|-----------------|
| 0.0 – 0.29 | AUTO ALLOW | `read_file`, `list_dir`, `grep` |
| 0.30 – 0.69 | ASK HUMAN | `write_file` to new path, `bash` (mild) |
| 0.70 – 0.99 | DENY (default) | `rm -rf`, `git push --force`, DB DROP |
| 1.0 | ALWAYS DENY | `.env` access, SSH keys, certs |

### 3.4 HITL Module Responsibilities

| Module | File | Lines | Purpose |
|--------|------|-------|---------|
| RiskEngine | `riskEngine.ts` | ~120 | Score risk 0–1, factor weighting |
| DestructiveGuard | `destructiveGuard.ts` | ~80 | Block destructive shell patterns |
| NetworkGuard | `networkGuard.ts` | ~70 | Restrict external network calls |
| SensitiveFiles | `sensitiveFiles.ts` | ~90 | Protect critical file paths |
| LoopGuard | `loopGuard.ts` | ~60 | Detect infinite agentic loops |
| SandboxRunner | `sandboxRunner.ts` | ~110 | Execute in restricted environment |
| AuditLogger | `auditLogger.ts` | ~80 | Record all decisions + outcomes |
| Autonomy | `autonomy.ts` | ~70 | Per-agent autonomy mode |
| RBAC | `rbac.ts` | ~100 | Role-based action permissions |
| SkillTrust | `skillTrust.ts` | ~60 | Trust level per skill source |

## 4. Agentic Tool-Calling Loop Design

### 4.1 Overview

The agentic loop is the core of the platform — it enables the LLM to reason, plan, and act iteratively using tools until a task is complete.

### 4.2 Tool-Calling Architecture

```
┌──────────────────────────────────────────────────────────────────────┐
│                      TEXT-BASED TOOL CALLING                          │
│                      (NOT native OpenAI JSON tools)                   │
└──────────────────────────────────────────────────────────────────────┘

  Why text-based?
  ─────────────
  Gateway models (MiniMax, etc.) do NOT support native function_call JSON
  → Platform uses XML-embedded tool calling in plain text
  → Universal compatibility with any OpenAI-compatible endpoint

  TOOL_USE_INSTRUCTIONS (injected into system prompt):
  ┌──────────────────────────────────────────────────────────────────┐
  │  To use a tool, output:                                          │
  │  <tool_use>                                                      │
  │    <name>tool_name</name>                                        │
  │    <parameter name="key">value</parameter>                       │
  │  </tool_use>                                                     │
  └──────────────────────────────────────────────────────────────────┘

  AGENTIC LOOP (in chat.ts):
  ┌──────────────────────────────────────────────────────────────────┐
  │                                                                  │
  │  round = 0                                                       │
  │  maxRounds = 15                                                  │
  │                                                                  │
  │  LOOP:                                                           │
  │  ┌────────────────────────────────────────────────────────────┐  │
  │  │  1. Build messages array:                                  │  │
  │  │     [system] [history (max 10 turns)] [user message]       │  │
  │  │                                                            │  │
  │  │  2. POST to LLM endpoint:                                  │  │
  │  │     { model, messages, max_tokens, temperature }           │  │
  │  │     (NO tools[] param — text-based only)                   │  │
  │  │                                                            │  │
  │  │  3. Parse LLM response for tool calls:                     │  │
  │  │     Format A: <tool_use><name>X</name>...</tool_use>       │  │
  │  │     Format B: <parameter name="k">v</parameter>            │  │
  │  │     Format C: JSON in <input> tag                          │  │
  │  │     Format D: Direct XML attribute tags                    │  │
  │  │                                                            │  │
  │  │  4. If tool calls found:                                   │  │
  │  │     → Execute each tool (tool-executor.ts)                 │  │
  │  │     → Append results to message history                    │  │
  │  │     → Increment round                                      │  │
  │  │     → Continue loop                                        │  │
  │  │                                                            │  │
  │  │  5. If no tool calls OR round ≥ maxRounds:                 │  │
  │  │     → Return final response                                │  │
  │  │     → BREAK                                                │  │
  │  └────────────────────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────────────────────┘
```

### 4.3 Available Tools (9 total)

| Tool | Description | Timeout | Security |
|------|-------------|---------|----------|
| `bash` | Execute shell command | HITL-gated | DestructiveGuard + SandboxRunner |
| `read_file` | Read file contents | No limit | SensitiveFiles check |
| `write_file` | Write/create file | No limit | Path validation |
| `list_dir` | List directory | No limit | Path validation |
| `grep_search` | Search file contents | No limit | Path validation |
| `web_fetch` | HTTP GET URL | 30s | NetworkGuard |
| `git_status` | Git repository status | 10s | ReadOnly |
| `git_diff` | Git diff output | 10s | ReadOnly |
| `git_log` | Git commit history | 10s | ReadOnly |

### 4.4 History Management

```
  History Buffer:
  ┌─────────────────────────────────────────────────────────┐
  │  Max messages: 20 (10 user+assistant turn pairs)        │
  │  Max chars: ~80-90 per message (truncated)              │
  │                                                         │
  │  [system prompt + skill context]                        │
  │  [user_1][assistant_1]                                  │
  │  [user_2][assistant_2]                                  │
  │  ...                                                    │
  │  [user_N][assistant_N]   ← current turn being built     │
  └─────────────────────────────────────────────────────────┘
```

## 5. Parallel Execution & Orchestration Design

### 5.1 Two-Level Concurrency System

```
┌──────────────────────────────────────────────────────────────────────┐
│             MULTI-AGENT EXECUTION SYSTEM                              │
│                                                                       │
│  Level 1: SubagentOrchestrator (dependency-aware DAG)                 │
│  ─────────────────────────────────────────────────────                │
│                                                                       │
│   User: "Build, test, and document a new feature"                     │
│              │                                                        │
│              ▼                                                        │
│   ┌─────────────────────────────────────────────────────────────┐    │
│   │  Orchestration Plan (DAG)                                   │    │
│   │                                                             │    │
│   │  Task A: "Implement feature"  (no deps)    → Build Agent   │    │
│   │  Task B: "Write tests"        (deps: [A])  → Test Agent    │    │
│   │  Task C: "Write docs"         (deps: [A])  → Docs Agent    │    │
│   │  Task D: "Code review"        (deps: [B,C])→ Review Agent  │    │
│   │                                                             │    │
│   │  Execution Order:                                           │    │
│   │  Round 1:  A (no deps, runs immediately)                   │    │
│   │  Round 2:  B + C (parallel, deps satisfied)                │    │
│   │  Round 3:  D (all deps done)                               │    │
│   └─────────────────────────────────────────────────────────────┘    │
│                                                                       │
│  Level 2: ParallelExecutionManager (fan-out / fan-in)                 │
│  ──────────────────────────────────────────────────────               │
│                                                                       │
│   User: "Analyze these 5 files"                                       │
│              │                                                        │
│              ▼  fan-out                                               │
│   ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                          │
│   │File1│ │File2│ │File3│ │File4│ │File5│  ← Parallel workers        │
│   └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘                          │
│      └──────────────────┬──────────────┘                             │
│                         │  fan-in                                     │
│                         ▼                                             │
│                  ┌─────────────┐                                      │
│                  │  Aggregator │  ← "Summarize:\n{results}"           │
│                  └─────────────┘                                      │
│                                                                       │
│  ScalableQueue:                                                       │
│  ───────────────                                                      │
│   - Workers: 4 (default)                                              │
│   - Max queue depth: 200                                              │
│   - Priority: HIGH | NORMAL | LOW                                     │
│   - Retry: configurable max retries with backoff                      │
│   - Backpressure: reject when queue full                              │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.2 Task State Machine

```
  ┌─────────┐
  │ PENDING │ ─────────────────────────────────────────────────┐
  └────┬────┘                                                   │
       │ worker picks up                                         │ manual cancel
       ▼                                                         │
  ┌─────────┐                                                    │
  │ RUNNING │ ──────────────── timeout/error ──────▶ ┌─────────┴─────┐
  └────┬────┘                                         │  CANCELLED    │
       │ success                                       └───────────────┘
       ▼
  ┌─────────────┐      ┌──────────┐
  │  COMPLETED  │      │  FAILED  │ ──── retry? ──▶ PENDING
  └─────────────┘      └──────────┘
```

## 7. Middleware Stack Design

### 7.1 Request Pipeline

```
  HTTP Request → Hono App
       │
       ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  1. LOGGER Middleware (logger.ts)                               │
  │     - Log: method, path, start time                             │
  │     - On response: log status, duration_ms                      │
  └───────────────────────────┬─────────────────────────────────────┘
                              │
  ┌───────────────────────────▼─────────────────────────────────────┐
  │  2. CORS Middleware (built-in Hono)                              │
  │     - Allow-Origin: * (all origins)                             │
  │     - Allow-Methods: GET, POST, PUT, DELETE, OPTIONS            │
  │     - Allow-Headers: Content-Type, Authorization, x-api-key    │
  └───────────────────────────┬─────────────────────────────────────┘
                              │
  ┌───────────────────────────▼─────────────────────────────────────┐
  │  3. RATE LIMITER (rate-limit.ts)                                │
  │     - Algorithm: sliding window (60s window)                    │
  │     - Limit: 120 requests/min per IP                            │
  │     - DDoS cap: track max 10,000 unique IPs                     │
  │     - On exceed: 429 Too Many Requests                          │
  └───────────────────────────┬─────────────────────────────────────┘
                              │
  ┌───────────────────────────▼─────────────────────────────────────┐
  │  4. AUTH Middleware (auth.ts)                                   │
  │     - Check: Bearer token OR x-api-key header                  │
  │     - If THIRDWAVE_API_KEY set: enforce                         │
  │     - If not set: allow all (open mode)                        │
  │     - On fail: 401 Unauthorized                                 │
  └───────────────────────────┬─────────────────────────────────────┘
                              │
  ┌───────────────────────────▼─────────────────────────────────────┐
  │  5. AUDIT WRAPPER (inline in server/index.ts)                  │
  │     - Wraps all /api/* routes                                   │
  │     - Records: timestamp, action, user, success, duration      │
  │     - Buffered writes: flush every 5 seconds                   │
  └───────────────────────────┬─────────────────────────────────────┘
                              │
                        ROUTE HANDLER
```

### 7.2 Rate Limiter Algorithm

```
  Per-IP sliding window:
  ┌──────────────────────────────────────────────────────────────┐
  │  Window: last 60 seconds                                     │
  │  Limit: 120 requests                                         │
  │                                                              │
  │  Time ──────────────────────────────────────────────────▶   │
  │       │←────── 60s window ──────────→│                      │
  │       [req][req][req]...[req]   count ≤ 120? ALLOW : 429    │
  │                                                              │
  │  Memory management:                                          │
  │  - Store timestamps in circular buffer per IP                │
  │  - Evict entries older than 60s on each request             │
  │  - Max 10,000 IPs in memory                                 │
  └──────────────────────────────────────────────────────────────┘
```

## 8. TUI Input Handling Design

### 8.1 Input Modes

```
┌──────────────────────────────────────────────────────────────────────┐
│                         TUI INPUT MODES                               │
└──────────────────────────────────────────────────────────────────────┘

  Normal Mode:                      Multi-line Block Mode:
  ─────────────                     ──────────────────────
  [ses] [agent] ❯ _                 [ses] [agent] ❯ """
  user types normally               user types:
  Enter = send                        line 1
                                      line 2
                                      line 3
  Continuation Mode:                """  ← closes block + sends
  ──────────────────
  [ses] [agent] ❯ fix this `\`
  (line continues)   ❯ and also this
  ❯ (Enter) = sends concatenated

  Paste Mode:                       Debounce:
  ────────────                      ─────────

  as pasted in rapid succession     for single-line imperceptibility
```
